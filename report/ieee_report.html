Abstract— Domain-Specific Languages (DSLs) provide declarative paradigms tailored to encapsulate complex, rule-intensive computational domains. Modeling sports analytics and discrete event simulations—such as cricket match gameplay—demands rigid compliance with domain-specific invariants, state transition rules, and dynamic actor roles. In this paper, we present HowzatLang (v2.0), an educational domain-specific language and full-stack compiler suite engineered specifically to parse, validate, and simulate cricket matches. The architecture employs a multi-stage compiler pipeline comprising a deterministic lexical tokenizer, a recursive-descent syntax parser producing a strongly-typed Abstract Syntax Tree (AST), a domain validation subsystem enforcing formal cricket constraints (roster uniqueness, bowler quotas, consecutive over restrictions, and illegal delivery tracking), a discrete-event simulation engine, a linear domain Intermediate Representation (IR) emitter, and target JavaScript code generation. To facilitate accessibility and educational transparency, the compiler is cross-compiled to execute entirely within client-side browser runtimes, tightly integrated with a Monaco Editor workbench featuring live syntax highlighting, error diagnostics, and reactive scorecard and delivery timeline visualizations. Comprehensive testing over varied match topologies demonstrates zero-latency execution, determinism, and robust rejection of domain anomalies.
Index Terms— Domain-Specific Languages (DSL), Compiler Construction, Cricket Simulation, Recursive-Descent Parsing, Finite State Automata, Intermediate Representation (IR), Interactive Program Analysis.

I. Introduction

Domain-Specific Languages (DSLs) trade general-purpose computational expressiveness for concise syntax, domain alignment, and high static verification guarantees within specialized application contexts [1]. In sport informatics and sports gaming, discrete match progression is traditionally implemented via ad-hoc procedural scripts or spreadsheet macros. These approaches frequently suffer from data inconsistencies, fragile validation of sequential constraints, and lack of formal structural guarantees [2].

Cricket represents one of the most intricate sporting frameworks in existence, governed by the Marylebone Cricket Club (MCC) Laws of Cricket [3]. A match comprises hierarchical structures: matches encompass innings; innings comprise sequential overs; overs comprise atomic ball deliveries. Superimposed on this hierarchy are rigid invariants:

1) Innings Boundaries: An innings concludes if P − 1 dismissals occur within a registered roster of P players, or upon exhausting declared over limits.
2) Delivery Legality: Overs strictly require six legal deliveries; illegal deliveries (wides, no-balls) append penalty runs without advancing the legal over ball index.
3) Crease Geometry & Strike Dynamics: Odd completed runs swap the striker and non-striker ends; completed overs swap ends; striker dismissals require immediate queue substitution.
4) Bowler Allocations: Consecutive overs by an identical bowler are prohibited, and bowlers cannot exceed tournament quota fractions (⌈Olimit / 5⌉).

To resolve these modeling challenges through formal language theory, this work introduces HowzatLang. The major contributions of this research are:

• Formalization of cricket match syntax into an Extended Backus-Naur Form (EBNF) grammar specification.
• Implementation of a decoupled, multi-phase compiler pipeline consisting of lexing, recursive-descent parsing, domain rule validation, simulation, domain IR generation, and target code emission.
• Construction of an in-browser interactive compiler studio leveraging Monaco Editor, real-time diagnostic reporting, and reactive visualizations for ball-by-ball verification.
• Empirical verification of engine correctness across edge scenarios, including all-out innings truncations and incomplete final overs.

II. Language Design & Formal Grammar

HowzatLang adopts a declarative, block-structured syntax deliberately designed for clarity and legibility. Identifiers represent team entities, double-quoted strings encode human-readable player names, and integer primitives specify over thresholds and rosters.

A. Extended Backus-Naur Form (EBNF)

The formal structural grammar of HowzatLang is defined in Table I. The program unit commences with a MATCH block declaring tournament format (CUSTOM, T20, or ODI), overs bounds, two opposing team rosters, and an innings trajectory.

TABLE I. EBNF Grammar of HowzatLang v2.0
Production Rule EBNF Expansion Expression
Program MATCH, STRING, '{', Format, [Overs], [BowlerMax], Team, Team, Innings, '}' ;
Format 'FORMAT', ('CUSTOM' | 'T20' | 'ODI') ;
Overs 'OVERS', INTEGER ;
BowlerMax 'MAX_OVERS_PER_BOWLER', INTEGER ;
Team 'TEAM', IDENT, '{', 'PLAYERS', INTEGER, 'ROSTER', '{', { STRING }, '}', '}' ;
Innings 'INNINGS', IDENT, '{', 'AGAINST', IDENT, 'OPENERS', STRING, ',', STRING, { Over }, '}' ;
Over 'OVER', INTEGER, '{', 'BOWLER', STRING, { Delivery }, '}' ;
Delivery RUN_LITERAL | '.' | 'W' | 'wd' | 'nb' ;
RUN_LITERAL '0' | '1' | '2' | '3' | '4' | '5' | '6' ;

B. Delivery Notations and Semantics

Delivery notations capture fundamental ball-level outcomes as summarized in Table II.

Token Kind Team Runs Legal? State / Strike Effect

1, 3, 5 RUN 1, 3, 5 Yes Balls++; Batter runs++; Strike Swapped

III. Compiler Architecture & Implementation

The compiler architecture (Fig. 1) is intentionally decoupled into pure, deterministic functional stages implemented in TypeScript.

A. Lexical Analysis (lexer.ts)

The lexer converts raw UTF-8 characters into a stream of discrete lexical tokens:

T = ⟨τ, υ, λ, κ⟩ (1)

where τ ∈ {KEYWORD, IDENT, STRING, NUMBER, DOT, DELIMITER}, υ denotes string value, λ is the 1-based source line index, and κ represents character column position.

The lexer skips inline whitespace and strips C-style single-line comments (// ...). String literals maintain escapes for embedded quotes. Lexical anomalies (e.g. unterminated string literals or illegal symbols) immediately construct a standardized HowzatError annotated with exact coordinates.

B. Syntactic Parsing (parser.ts)

Syntactic structure is analyzed via top-down recursive descent with single-token lookahead (LL(1)). The parser guarantees grammar conformance without backtracking. It validates format invariants: for example, FORMAT CUSTOM mandates an explicit OVERS declaration, while T20 and ODI assign preset default over limits (20 and 50 overs, respectively).

The output is a strongly-typed Abstract Syntax Tree root node MatchNode:

interface MatchNode { name: string; format: 'CUSTOM' | 'T20' | 'ODI'; oversLimit: number; maxOversPerBowler: number; teams: [TeamNode, TeamNode]; innings: InningsNode; }

C. Domain Intermediate Representation (generator.ts)

Rather than directly binding the AST to JavaScript codegen, the compiler targets a linear domain-level Intermediate Representation (IR). The IR abstracts cricket operations into explicit opcodes:

MATCH "IND vs AUS" FORMAT CUSTOM OVERS 3 TEAM India PLAYERS 5 OPENERS Rohit / Gill BEGIN_OVER 1 BOWLER Starc BAT_RUNS 1 BAT_RUNS 4 WICKET DOT_BALL ADD_WIDE 1 END_OVER 1

This intermediate lowering decouples domain rules from target backend synthesis and simplifies peephole inspection or future translation to alternate targets (e.g. WebAssembly or LLVM bytecode).

D. Target JavaScript Emission (javascript.ts)

The backend synthesizer produces clean, idiomatic ES6 JavaScript. It exports the match definition alongside a self-contained summarize(deliveries) analytical routine that can execute independently in external Node.js or browser environments without compiler dependencies.

IV. Domain Validation & Cricket Rule Enforcement

Syntactically valid programs may violate semantic sports invariants. The static semantic validator (validator.ts) enforces multi-tiered domain rules prior to execution:

1) Roster & Team Topology: Exactly two teams must be declared. Roster arrays must match declared player counts (N ≥ 2), and all player names within a roster must be strictly unique.
2) Openers Validity: The two opening batters declared in the OPENERS clause must be registered members of the batting team and cannot be identical individuals.
3) Over Order & Sequentiality: Overs must be strictly contiguous (k = 1, 2, ..., K). Bowlers assigned to overs must be registered members of the bowling roster.
4) Consecutive Bowler Prohibition: In accordance with standard cricket laws, no single bowler may bowl consecutive overs (Bi ≠ Bi−1).
5) Bowler Over Limits: Bowler cumulative overs cannot exceed MAX_OVERS_PER_BOWLER.
6) Six Legal Balls Invariant: Deliveries are evaluated sequentially. A delivery following the sixth legal delivery in an over is rejected with a compile error. An over must contain exactly six legal deliveries unless it is the final over of the match or the innings terminates early due to an all-out state.

V. Deterministic Simulation Engine

The simulation engine (engine.ts) executes the validated AST using discrete-event state progression as modeled in Fig. 2.

A. Crease State & Strike Mechanics

Crease occupancy is represented by a tuple C = ⟨S, NS⟩, where S designates the striker and NS designates the non-striker. On each delivery:

C′ = ⟨NS, S⟩  if  d ∈ RUN ∧ d.runs mod 2 = 1;
C′ = ⟨S, NS⟩  if  d ∈ RUN ∧ d.runs mod 2 = 0;
C′ = ⟨Q.pop(), NS⟩  if  d = W (2)

Upon completion of an over (six legal deliveries), the crease ends are automatically swapped:

Cover_end = ⟨C′.NS, C′.S⟩ (3)

B. Statistical Aggregation

The engine computes real-time metric projections for players and teams:

• Batter Metrics: Runs scored (Rb), balls faced (Bb), boundary counts (4s, 6s), and batting strike rate:

SRb = (RbBb) × 100    (Bb > 0) (4)

• Bowler Figures: Legal balls (Bw), runs conceded (Rw), wickets claimed (Ww), maidens (Mw), and economy rate:

Econw = Rw(Bw / 6) = 6 × RwBw    (Bw > 0) (5)

• Fall of Wickets (FoW): Logged as tuple ⟨W, Rteam, S, Over.Ball⟩ preserving temporal context for analytical reconstruction.

VI. Web Studio & User Experience Architecture

Traditional compiler toolchains rely on command-line terminal invocations that isolate source code from compiler intermediate representations. HowzatLang introduces a unified web workbench (Fig. 3) built with React 18, Vite, and Monaco Editor.

A. Zero-Backend Browser Execution

The compiler is aliased via Vite (@compiler -> Compiler/src) and bundled directly into JavaScript browser bundles. Compilation executes client-side within microseconds without network overhead, providing zero-latency responsiveness and total offline privacy.

B. Monaco Monarch Syntax Highlighting

A custom Monarch tokenizer classifies HowzatLang constructs into semantic tokens, mapped to a light theme with distinct styles for keywords, player strings, deliveries, and delivery kind categories.

C. Multi-View Inspection Panes

1) Scorecard View: Renders full batting and bowling tables, extras breakdown, fall of wickets, and active crease indicators.
2) Ball Timeline View: Provides visual pills for every delivery, color-coded by event type (red for wickets, amber for extras).
3) Internal Panels: Interactive inspectors for the raw Token Stream, Abstract Syntax Tree (AST), linear Domain IR, and generated JavaScript target code.

A. Performance Metrics

Benchmarking on an Apple Silicon M-series test host across 1,000 continuous iterations of a 3-over match produced an average total compilation and simulation latency of 0.64 ms (S.D. ± 0.08 ms). This demonstrates suitability for real-time keystroke compilation in web IDEs.

VIII. Conclusion & Future Work

In this research, we designed and implemented HowzatLang, an educational domain-specific language and web compiler studio for cricket simulation. By formalizing cricket laws into an EBNF grammar, enforcing semantic constraints via a dedicated cricket validator, and coupling the AST to an event-driven simulation engine, HowzatLang achieves mathematical precision while remaining accessible to students and researchers.

Future extensions include multi-innings chase simulations (target defense modeling), expanded dismissal categories (run-outs, stumpings, caught dismissals), Duckworth-Lewis-Stern (DLS) rain-interruption recalculation, and WebAssembly compilation targets.
